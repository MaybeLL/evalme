## 第一轮发现与决定

| 优先级 | 发现 | 讨论后的决定 |
| --- | --- | --- |
| P1 | 只检查反馈引用不足以保护删除边界；数据库普通外键也允许跨系列版本链与更正链 | 审计所有关联边、系列根及链完整性；预览和执行阻止异常，不扩删其他系列 |
| P1 | token 规范及数据库身份未定，客户端和 SQL 双实现可能不一致 | 持久 database_uuid；provider-specific token；PG 共享服务端计划函数，SQLite 共享本地函数；摘要覆盖完整记录与关联，而非只看数量或 payload_hash |
| P1 | advisory lock 不能阻止直接 SQL，循环外键方案尚未落定 | PG 固定顺序表锁、READ COMMITTED 锁后重读、指定可延迟外键；SQLite BEGIN IMMEDIATE 与事务级延迟外键；提交前强制完整性检查 |
| P1 | 现有结构检查仅看函数和触发器名字，无法证明 SECURITY DEFINER 安全性 | 校验函数定义、签名、安全设置、owner、有效授权及触发器定义/状态；受限 owner，安装与授权同事务 |
| P2 | 存储版本与业务记录版本混用，缺少具体迁移入口 | 存储 v2、业务行版本仍为 1；显式 db migrate；新 CLI 兼容 v1 日常业务但不允许删除；迁移前更新全部客户端 |
| P2 | 被阻塞的 dry-run 成功/错误形态不明确 | 检查完成返回 can_delete=false 与结构化 blockers，不给可执行 token；实际执行返回稳定阻塞错误 |

共同认可并保留的范围：整题系列永久删除、全部练习与评价更正历史一并清理、话题保留、默认取消、范围变化重新确认、提交结果未知不宣称成功、不做回收站或批量删除。

## 第二轮复审

独立审查修订后的完整文档，确认上述问题均已落实。补充两个实现细节：

1. v1 尚无 database_identity，迁移锁定现有元数据与业务表后在事务内创建它；不能对不存在的表执行锁语句。v2 使用完整固定锁顺序，两者继续使用同一 advisory lock。
2. 入口函数授权检查应承认受控 owner 的固有权限；owner 之外只有声明的应用角色可获得有效 EXECUTE，不能只检查直接 GRANT 而遗漏继承授权。

复核最终设计第 7、8 节，主 agent 已将这两项纳入最终设计。粗粒度表锁会限制短时间并发写入，但对当前 MVP 比细粒度锁和复杂通用写入 API 更容易验证；锁等待有界且确认期间不持锁，属于接受的取舍。

备份与克隆保留 UUID 时被视为同一逻辑库，文档已明确这一限制；不声称 token 能区别内容完全相同的克隆。独立克隆需管理员在开放访问前更换身份。

## 一致结论

**主 agent 与独立审查 agent 一致同意修订版作为第一版实现基线，没有剩余阻塞性问题或设计分歧。**

该结论仅表示设计 review 达成一致，不代表实现完成、测试通过、历史数据无异常或生产迁移获得授权。实现时仍必须完成文档中的 SQLite、真实隔离 PostgreSQL、并发、权限、失败回滚和 PTY 验收；不能把讨论结果当作运行证据。

## 实现复审（2026-10-22）

同一独立 reviewer 对实现进行两轮只读审查。首轮发现 SQLite 缺少结构/完整外键验证、PostgreSQL 元数据权限未覆盖列级授权；主实现先补失败测试，再修复。复核确认两项均已解决，并检查提交前取消/提交期间结果不明、CLI 默认取消/机器令牌/迁移确认的边界，未发现剩余阻塞问题。

实际测试由主实现运行：Node 22.16.0 与 24.21.0 各 107 项通过、0 失败、0 跳过。证据与适用范围见 [TDD 验收](../mvp/evidence/task-deletion-tdd.md)。不将此结果视为生产迁移或真实跨机验收。
