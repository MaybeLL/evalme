# EvalMe 初始化体验设计独立 Review

日期：2026-10-22
审查对象：`docs/init-experience-design.md`，本报告行号对应本次审查版本。
方式：静态核对设计与配置、Clack 向导、schema、存储事务及部署脚本；未连接生产数据库、未读取凭据、未执行数据库测试。

## 结论

设计方向合理，建议在进入实现前修正以下 3 项。没有要求扩大到数据库安装、建库或自动迁移。特别需要先明确已有部署的权限兼容策略，避免本次安装体验优化阻断已经可用的共享数据库。

## 发现

### P1：schema_meta 权限新要求与现有部署不兼容，且与“不撤销权限”冲突

- **位置**：设计第 66、78、98 行。
- **证据**：`mvp/scripts/deploy/postgres-mac.mjs:101-102` 为应用账号授予所有表的 SELECT、INSERT，并设置同样的默认权限，因此包括 `schema_meta`。`mvp/src/config.mjs` 的 `assertRuntimePrivileges` 目前只要求元数据表可读，不禁止其 INSERT。设计却把“schema_meta 不授予写权限”写入 READY 条件。
- **影响**：如果此句表示拒绝现有 INSERT 权限，已部署数据库会从可用变成不兼容；若仅表示本次不主动授予，管理身份的既有默认权限仍可能自动授予 INSERT，使新初始化无法达到预期。文档同时规定不撤销其他权限，当前行为没有闭合。
- **建议**：明确区分“新库授权基线”和“既有库兼容策略”。本次可以保留现有 schema_meta INSERT 的兼容性，新库只显式授予其 SELECT；若一定要严格禁止，则提供独立、明确授权的权限调整流程，并处理管理角色默认权限产生的授权，不要让普通只读连接路径隐式修改权限。补充使用现有部署脚本创建数据库后执行新版 init 的回归案例。

### P2：空库分支缺少替换旧配置的确认时点

- **位置**：设计第 53、64-70、93 行。
- **证据**：READY 分支明确要求确认替换旧配置；UNINITIALIZED 分支只有远端初始化确认，随后直接保存本机配置。现有 `initializeSaved` 会在数据库操作之前检测配置冲突，CLI 再通过 `confirmReplacement` 确认，原实现具有这层保护。
- **影响**：设备已有数据库 A 配置，用户连接空库 B 时，按空库流程可能覆盖 A 配置而没有明确确认；或者直到 B 已经建好才提示配置冲突，用户拒绝后留下意料外的远端修改。
- **建议**：把配置替换确认提升为所有路径的共同规则，且发生在任何初始化写入之前。可以将“初始化 B 并将这台设备从 A 切换到 B”合并为一个清楚的最终确认。明确目标相同但凭据更新时的规则。增加旧配置 A → 空库 B 的确认、拒绝与失败验收。

### P2：提交后应用身份验证失败的结果与恢复流程未定义

- **位置**：设计第 70、90-94、114 行。
- **证据**：流程在远端提交之后才用应用账号重连验证；故障章节只明确了提交失败、提交结果不明和本机保存失败。现有配置初始化同样在建表后调用 `checkSchema` 与 `assertRuntimePrivileges`，这里可能独立失败。
- **影响**：DDL 已成功提交后，应用账号可能因网络中断、角色权限或默认授权问题未通过验证。不能承诺回滚，也不能保存未经验证的连接；仅报通用错误会让用户误以为初始化没有发生。
- **建议**：增加独立结果“数据库结构已初始化，应用连接验证未通过，旧配置保持不变”，按网络/权限原因给出下一步。再次 init 只读检测；权限缺失引导管理员调整，不能重新把已存在的结构视为空库。增加提交后重连失败及权限验证失败测试。

## 通过点与实现提示

- 默认本机保存与共享 PostgreSQL 的选择贴合用户任务；移除默认 JSON 提问、仅在必要时收集管理身份，有效减少术语负担。
- 不存在的数据库与空 schema 明确分开；权限不可见不等于不存在，拒绝部分结构自动修复，边界正确。
- 临时管理员与应用账号分离，与现有运行时最小权限策略一致；同目标校验和角色标识符安全引用保留了必要约束。
- 事务和并发设计可实施：现有 `Store.transaction` 已采用事务级 advisory lock 和有限 lock_timeout，应复用同一锁约定；重新检测、DDL 和 GRANT 必须处于同一连接的同一事务，不能只在外层包现有独立提交的 initialize。
- 状态检测确实需要新增能力：当前 `checkSchema` 只检查版本行，schema 定义之外还有 `core.mjs` 追加的 PostgreSQL 外键，统一契约必须覆盖它。不能把原有版本检查直接当作 READY 检测。
- 非交互模式的显式管理员参数保留合理；严格拒绝不完整结构是预期的安全行为变化，应在实现说明中明确，而非声称所有旧行为原样保留。

## 建议决策

接受总体方案，先修正文档中的权限兼容策略、所有分支的替换确认时点及提交后验证失败处理，再开始实现。本报告不代表实现验收通过。
